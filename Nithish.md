## 1. Problem Statement

### Current (Bad) Shape

**`teams` collection:**
- Hundreds of individual documents, one per team.
- Every Admin, Jury, and Team-Dashboard page hits Firestore with a full `.get()` or `.where()` call directly inside Server Actions.
- No API boundary — Firestore Admin SDK is called scattered across 5+ files.

**`evaluations` collection:**
- Hundreds of individual documents, one per `{round}_{juryId}_{teamId}`.
- Queries scatter across Admin actions (`getAllEvaluationsAdmin`), Jury actions (`getJuryDashboardData`, `submitAndFreezeEvaluation`), and more.

### Target (Good) Shape

| Collection    | Old                              | New                                    |
|---------------|----------------------------------|----------------------------------------|
| `teams`       | N docs, 1 per team               | **5 docs**, 1 per domain/theme         |
| `evaluations` | N docs, 1 per evaluation record  | **2 docs**, 1 per round (prelims/finale) |

All Firestore access is moved **exclusively** behind `src/app/api/` Route Handlers. No Server Action or page component should ever import `firebase-admin` or call `db.collection()` directly again.

### 2.2 `evaluations` Collection — 2 Round Documents

**Document IDs** (fixed):
```
evaluations/prelims
evaluations/finale
```

Each document:

```jsonc
{
  "round": "prelims",
  "totalCount": 87,
  "updatedAt": "<timestamp>",
  "records": [
    {
      "id": "prelims_J001_abc123",
      "teamId": "<team.id inside the teams array>",
      "teamName": "Team Alpha",
      "displayId": "HW-001",
      "domainId": "autonomous-agentic-ai",
      "juryId": "jury@example.com",
      "juryName": "Dr. Smith",
      "rubric": {
        "conceptStrength": 10,
        "buildIntelligence": 11,
        "deliveryImpact": 7,
        "liveDefenseScore": 6,
        "communication": 9
      },
      "totalScore": 43,
      "remarks": "Strong demo.",
      "feedback": "Work on delivery.",
      "highlighted": false,
      "isFrozen": true,
      "migratedFrom": "evaluations/<old_doc_id>",
      "createdAt": "<timestamp>",
      "updatedAt": "<timestamp>"
    }
  ]
}
```

> **Key rule:** Records are appended via `FieldValue.arrayUnion()`. Updates are done by reading the doc, patching the matching record in memory (by `id`), then writing back the full `records` array — wrapped in a Firestore **transaction** to prevent concurrent write conflicts.

## 3. What Changes vs What Stays the Same

| Aspect | Before | After |
|---|---|---|
| `teams` doc count | N (one per team) | **5** (one per theme) |
| `evaluations` doc count | N (one per eval) | **2** (prelims + finale) |
| Team lookup by `teamId` | `db.collection('teams').doc(teamId).get()` | Read domain doc → find in `teams[]` array |
| Evaluation write | `db.collection('evaluations').doc(id).set()` | `arrayUnion` into `evaluations/prelims` or `/finale` |
| Firestore access location | Scattered in Server Actions and page files | **Only** in `src/app/api/**` Route Handlers |
| `roles`, `labs`, `finalLabs`, `gameScores`, `metadata` | **Unchanged in structure** | Access point changes (moved to API routes) |

## 4. New API Layer Map

All routes live under `src/app/api/`. Every route is a Next.js Route Handler (`route.ts`). Auth is verified server-side inside each route using the session cookie.

## 5. Phase-by-Phase Implementation Plan

### Phase 1 — Data Migration Script

**Goal:** Write a one-time script that reads the old Firestore structure and writes to the new one. Old data is preserved until Phase 5 validation is complete.

**File to create:** `src/scripts/migrate-to-new-schema.ts`

#### Step 1.1 — Migrate `teams` collection

```
Algorithm:
1. Read all docs from old `teams` collection.
2. For each team doc:
   a. Determine its domain via the existing resolveTeamTheme() logic.
   b. Map the domain name to its new document ID slug:
      "Autonomous Agentic AI"                    → "autonomous-agentic-ai"
      "Adaptive Intelligent Systems"             → "adaptive-intelligent-systems"
      "Predictive Logistics using Industrial AI" → "predictive-logistics-industrial-ai"
      "AI for Smart Business Solution"           → "ai-smart-business-solution"
      "Human Centered AI"                        → "human-centered-ai"
   c. Build a team object preserving the original auto-generated doc.id
      as the team's `id` field inside the array.
   d. Group all team objects by their target domain slug.
3. For each of the 5 domain slugs, write the domain document:
   { domainId, domainName, teamCount, updatedAt, teams: [...] }
4. Write a migration log to `metadata/migrationLog`.
```

**Validation after Step 1.1:**
- Sum of all `teamCount` fields across 5 docs == old `teams` collection total.
- Each team `id` is unique and matches an original Firestore doc ID.

#### Step 1.2 — Migrate `evaluations` collection

```
Algorithm:
1. Read all docs from old `evaluations` collection.
2. Read all 5 new domain docs to build a teamId → domainId lookup map.
3. Split evaluation docs into two groups: round === 'prelims' and round === 'finale'.
4. For each evaluation record:
   a. Preserve old doc.id as the record's `id` field.
   b. Add `domainId` by looking up teamId in the map from step 2.
   c. Add `migratedFrom: "evaluations/<old_doc_id>"`.
5. Write prelims group as the `records` array of `evaluations/prelims`.
6. Write finale group as the `records` array of `evaluations/finale`.
7. Set `totalCount` on each.
```

**Validation after Step 1.2:**
- `evaluations/prelims.records.length` == old `prelims` doc count.
- `evaluations/finale.records.length` == old `finale` doc count.
- All `id` values inside records are unique.

#### Step 1.3 — Do NOT delete old collections yet

Keep old `teams` (N docs) and `evaluations` (N docs) as a backup until Phase 5 is complete.

### Phase 2 — Build API Route Handlers

**Goal:** Create all Route Handlers listed in Section 4. Each route must:
- Verify the session cookie using `getAdminAuth().verifySessionCookie()`.
- Check the caller's role (admin / jury / coordinator / team) from `roles` collection.
- Read/write **only** to the new schema.
- Return structured JSON: `{ success: boolean, data?: any, error?: string }`.

#### Step 2.1 — Create shared utilities

**File:** `src/lib/api-utils.ts`
```
Exports:
- verifySessionAndGetRole(request: NextRequest):
    Promise<{ email, role, juryId?, juryName? } | null>
- apiSuccess(data: any, status?: number): NextResponse
- apiError(message: string, status?: number): NextResponse
- requireRole(allowedRoles: string[], role: string): boolean
```

**File:** `src/lib/firestore-helpers.ts`
```
Exports:
- DOMAIN_DOC_IDS: string[]   — the 5 fixed slugs
- getDomainDocId(theme: string): string
    Maps a theme name to its Firestore slug.
- findTeamInDomainDocs(teamId: string):
    Promise<{ team, domainId, domainDocRef } | null>
    Reads all 5 domain docs (parallel); searches teams[] for matching id.
- findEvalRecord(round: 'prelims'|'finale', evalId: string):
    Promise<{ record, index } | null>
    Reads the correct evaluations doc; searches records[] for matching id.
```

#### Step 2.2 — Teams routes

```
src/app/api/teams/route.ts
  GET  → Read all 5 domain docs in parallel; merge teams[] arrays;
          apply ?domain= / ?leadEmail= filters in memory.
  POST → Validate payload, determine domain, run transaction:
          read domain doc → check teamName uniqueness →
          push new team object → increment teamCount.

src/app/api/teams/stats/route.ts
  GET  → Read all 5 domain docs; return { [domainId]: teamCount, total }.

src/app/api/teams/leaderboard/route.ts
  GET  → Read all 5 domain docs; flatten teams[]; sort by totalGameXP desc;
          return ranked array.

src/app/api/teams/[teamId]/route.ts
  GET    → findTeamInDomainDocs(teamId) → return team object.
  PATCH  → findTeamInDomainDocs(teamId) → patch fields in array →
            transaction write back full teams[] array. Also sync labs if
            assignedLabId changed.
  DELETE → findTeamInDomainDocs(teamId) → remove from array →
            transaction write back. Decrement teamCount. Sync lab count.
```

#### Step 2.3 — Evaluations routes

```
src/app/api/evaluations/route.ts
  GET  → Read evaluations/<round> doc; return records[] filtered by
          ?juryId= / ?teamId= if provided.
  POST → Validate payload; build record with id = `{round}_{juryId}_{teamId}`;
          check for duplicate id in records[];
          run transaction: arrayUnion new record; increment totalCount.

src/app/api/evaluations/[evalId]/route.ts
  PATCH  → findEvalRecord(round, evalId);
            patch fields in memory; transaction write back full records[].
  DELETE → findEvalRecord(round, evalId);
            transaction: filter out record; decrement totalCount.

src/app/api/evaluations/publish-prelims/route.ts
  POST → Read `evaluations/prelims.records`; group by teamId; compute averages;
          batch-update each team in their domain doc (fieldPath patch inside
          teams[] array using transaction).
```

#### Step 2.4 — Other collection routes

Follow identical patterns for `labs`, `final-labs`, `game-scores`, `roles`, `metadata/timelines`, `metadata/winners`, and `stats`. These routes read/write standard (non-array-embedded) Firestore docs and are straightforward CRUD.

## 7. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Firestore 1 MB doc limit** — A domain with many teams could push the 5 domain docs over the limit. | High | Monitor doc sizes post-migration. If any domain doc exceeds ~200 teams (estimated safe limit), split into shards (`autonomous-agentic-ai-1`, `-2`) with a top-level count doc. |
| **Concurrent team registrations** — Two simultaneous writes to the same domain doc may conflict without a transaction. | Medium | Wrap `POST /api/teams` in a Firestore `runTransaction()`. |
| **Evaluation array update atomicity** — Patch-in-array (read-modify-write) is unsafe without a transaction. | Medium | Wrap all `PATCH /api/evaluations/[evalId]` writes in `runTransaction()`. |
| **O(N) team lookup by teamId** — `findTeamInDomainDocs` reads all 5 docs and scans arrays. | Low-Medium | Cache the 5 domain docs using `unstable_cache` (already in the codebase). Cache miss triggers a full read; cache hit is instant. |
| **Migration downtime risk** — Registrations during migration would miss the new schema. | Medium | Run migration **after** setting `timeline1.enabled = false` via admin panel to close registration. |
| **Rollback safety** — If the new schema has bugs, reverting must be fast. | High | Old N-document collections are preserved (not deleted) until Phase 5 is signed off. Rollback = revert Server Actions to old `db.collection()` calls. |
